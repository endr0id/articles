# デザインパターンとは？
デザインパターンとは、**「ソフトウェア設計で繰り返し起きる問題に対する、再利用可能な設計上の解決方法」**のことです。

※完成済みのコードやライブラリではありません。

## デザインパターンは「設計の型」
例えば、次のような状況を考えてみます。
> 「同じ処理を行いたいが、状況によって処理方法を切り替えたい」

この問題は様々なシステムで繰り返し登場します。

具体例として、商品の割引計算を考えてみましょう。

```typescript
function calculatePrice(
  price: number,
  discountType: "normal" | "premium",
) {
    if (discountType === "normal") {
        return price * 0.9;
    }

    if (discountType === "premium") {
        return price * 0.8;
    }
};
```

この方法でも動作します。

しかし、割引の種類が増えると `if (...)` の様な条件分岐は増えていきます。

そこで、割引処理そのものを分離してみます。

```typescript
type DiscountStrategy = (price: number) => number;

function calculatePrice(
  price: number,
  strategy: DiscountStrategy,
) {
  return strategy(price);
};

const normalDiscount: DiscountStrategy = (price) => price * 0.9;
const premiumDiscount: DiscountStrategy = (price) => price * 0.8;
```

使用側では、次のように処理方法を柔軟に差し替えられます。

```typescript
calculatePrice(1000, normalDiscount);
calculatePrice(1000, premiumDiscount);
```

このように、「処理方法を別のオブジェクトや関数として切り替えられるようにする」という設計の考え方を「Strategy Pattern」と呼びます。

ここで重要なのは、`DiscountStrategy` という名前をつけることではありません。

💡 **本質**

「処理方法を切り替えたい」という問題に対して、**「処理方法を外から差し替えられる構造にする」**ということです。

## なぜデザインパターンが必要なのか
ソフトウェア開発では、似たような設計上の問題が何度も登場します。

- オブジェクトをどう生成するか
- 異なるインターフェースをどう接続するか
- 処理方法をどう切り替える
- 状態の変化をどう通知するか
- 複雑な処理をどう隠蔽するか

これらを毎回0から考えることもできます。

しかし過去に多くの開発者が同じような問題に遭遇し、様々な解決方法を試行錯誤してきました。

その中で「この問題にはこのような構造が有効だった」という**知識が整理され、名前がつけられたもの**がデザインパターンです。

## デザインパターンは「設計の共通語彙」
例えば、開発者同士で「この処理はStrategy Patternにしよう」と会話したとします。

これは単に「Strategyという名前のクラスを作る」という意味ではありません。

チーム内で「処理の具体的な実装を切り替えられるように、処理方法を分離しよう」という設計意図を一言で正確に共有できているということです。

つまりデザインパターンは「設計上の問題とその解決方法を共有するための共通語彙」としても機能します。

## デザインパターンを学ぶ目的
デザインパターンを学ぶ目的は**コードをパターンに当てはめることではありません。**

最初から「Singletonを使おう」「Observerを使おう」のようにパターンを適用することをゴールにしてはいけません。

**まず設計上の問題を発見すること**です。

```text
 設計上の問題を発見する  
     ↓  
 問題の原因を考える  
     ↓  
 適切な構造を考える  
     ↓  
 既知のデザインパターンを解決策の候補として利用する
```

例えば「このクラスが具体的な実装に依存しすぎている」という問題があれば以下の様なパターンが解決策の候補になります。

- Factory
- Adapter
- Dependency Injection

また「処理方法を状況に応じて切り替えたい」という問題であれば次のパターンが候補になります。

- Strategy
- State

このようにデザインパターンは「設計上の問題に対する解決策の引き出し」として利用します。

## 「名前」ではなく「問題と構造」が重要
次のコード見てみましょう。

```typescript
const service = new Proxy(target, {
  get(target, property) {
    return target[property];
  },
});
```

これはJavaScriptの `Proxy` APIを使用したコードです。

しかし、`Proxy` APIを使ったから「Proxy Pattern」というわけではありません。

```text
Client → Proxy → Real Object
```

本質的には「本物のオブジェクトへのアクセスを代理オブジェクト経由にする」という構造を採用しているため、「Proxy Pattern」と呼ばれます。

デザインパターンを理解するときは「何というAPIを使っているか」ではなく「どのような設計上の問題をどのような構造で解決しているか」を見ることが重要です。

## デザインパターンには「適用範囲」がある
デザインパターンという言葉は広く使われていますが全てのパターンが同じ範囲（スコープ）の問題を解決するわけではありません。

```text
オブジェクト → モジュール → アプリケーション → システム全体
```

この様に対象とする設計の大きさが異なります。

1. オブジェクトレベル

    主にクラスや関数、オブジェクト同士の関係といった**比較的小さな範囲**を扱います。

    - Observer  
    - Strategy  
    - Factory  
    - Proxy  
    - Adapter

2. モジュール・アプリケーションレベル

    アプリケーション内の責務（役割）を分離するような、**より大きな範囲**を扱います。

    - Repository  
    - Service Layer  
    - Dependency Injection  
    - MVC

3. システムレベル

    複数のサービスや**システム全体の構造**を扱います。

    - Microservices
    - Event-Driven Architecture
    - CQRS

## 代表的なデザインパターンと解決する問題
デザインパターンは「どの様な問題を解決するためのパターンなのか」という視点で整理すると理解しやすくなります。

| 解決したい問題 | 代表的なパターン |
| --- | --- |
| オブジェクトの生成方法を隠したい | Factory |
| 生成するオブジェクトを1つに制限したい| Singleton |
| 既存のインターフェースを別の形に変換したい | Adapter |
| 既存のオブジェクトに機能を追加したい | Decorator |
| 複雑な処理を単純なAPIで隠したい | Facade |
| 本物のオブジェクトへのアクセスを代理したい | Proxy |
| 処理方法を切り替えたい | Strategy |
| 状態の変化を他のオブジェクトに通知したい | Observer |
| 状態によって振る舞いを変えたい | State |
| 処理を複数の処理に順番に渡したい | Chain of Responsibility |
| 依存するオブジェクトを外から渡したい | Dependency Injection |

## まとめ
デザインパターンとは「ソフトウェア設計で繰り返し起きる問題に対する、名前の付いた再利用可能な解決方法」です。

重要なのはパターン名を暗記してコードを無理やり当てはめることではありません。

💡 **学習のステップ**
1. 設計上の問題を発見する  
2. 問題に適した構造を考える  
3. 既知のパターンを「解決策の候補」として利用する

デザインパターンはコードの書き方のテンプレートではなく「設計上の問題を解決するための知識体系」です。

学ぶときは「このパターンは何か？」ではなく「どんな問題を解決するためにこの構造が使われるか？」という視点で整理するとパターンの本質を深く理解できる様になります。
