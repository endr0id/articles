# デザインパターンとは？
デザインパターンとは以下の様な考えです。
> ソフトウェア設計で繰り返し起きる問題に対する、再利用可能な設計上の解決方法

ただし、**完成済みのコードやライブラリではありません。**

## デザインパターンは「設計の型」
例えば、次のような問題があるとします。
> 「同じ処理を行いたいが、状況によって処理方法を切り替えたい」

この問題は様々なシステムで繰り返し登場します。

例えば、商品の割引計算を考えます。

```typescript
function calculatePrice(
  price: number,
  discountType: "normal" | "premium",
) {
    if (discountType === "normal") {
        return price * 0.9;
    }

    if (discountType === "premium") {
        return price * 0.8;
    }
}
```

この方法でも動作します。

しかし、割引の種類が増えると、

```typescript
if (...)
if (...)
if (...)
if (...)
```

のように条件分岐が増えていきます。

そこで割引処理そのものを分離します。

```typescript
type DiscountStrategy = (price: number) => number;

function calculatePrice(
  price: number,
  strategy: DiscountStrategy,
) {
  return strategy(price);
}

const normalDiscount: DiscountStrategy = (price) => {
    return price * 0.9;
}

const premiumDiscount: DiscountStrategy = (price) => {
    return price * 0.8;
}
```

使用側では

```typescript
calculatePrice(1000, normalDiscount);
calculatePrice(1000, premiumDiscount);
```

のように、処理方法を差し替えられます。

このような
> 処理方法を別のオブジェクトや関数として切り替えられるようにする

と言う設計の考え方を **Strategy Pattern** と呼びます。

重要なのは、`DiscountStrategy` という名前をつけることではありません。

本質は
> 「処理方法を切り替えたい」という問題に対して、「処理方法を外から差し替えられる構造にする」

ということです。

## なぜデザインパターンが必要なのか
ソフトウェア開発では、似たような設計上の問題が何度も登場します。

- オブジェクトをどう生成するか
- 異なるインターフェースをどう接続するか
- 処理方法をどう切り替える
- 状態の変化をどう通知するか
- 複雑な処理をどう隠蔽するか

と言った様な問題です。

これらを毎回考慮こともできます。

しかし、過去に多くの開発者が同じような問題に遭遇し、様々な解決方法を考えてきました。

その中で
> この問題には、このような構造が有効だった

という知識が整理され、名前が付けられています。

それが**デザインパターン**です。

## デザインパターンは「設計の共通語彙」
例えば、開発者同士で
> 「この処理はStrategy Patternにしよう」

と言ったとします。

このとき、単に「Strategyという名前のクラスを作る」という意味ではありません。

一般的には
> 「処理の具体的な実装を切り替えられるように、処理方法を分離しよう」

という設計意図を共有しています。

つまり、デザインパターンは
> 設計上の問題と、その解決方法を共有するための共通語彙

としても機能します。

## デザインパターンを学ぶ目的
デザインパターンを学ぶ目的は**コードをパターンに当てはめること**ではありません。

例えば

> 「Singletonを使おう」
>
> 「Factoryを使おう」
>
> 「Observerを使おう」

の様な最初からパターンを適用することが目的ではありません。

重要なのはまず設計上の問題を発見することです。

> 設計上の問題を発見する
>
>     ↓
>
> 問題の原因を考える
>
>     ↓
>
> 適切な構造を考える
>
>     ↓
> 既知のデザインパターンを解決策の候補として利用する

という流れで
> 「このクラスが具体的な実装に依存しすぎている」

という問題があれば

- Factory
- Adapter
- Dependency Injection

などが解決策の候補になります。

また
> 処理方法を状況に応じて切り替えたい

という問題があれば

- Strategy
- State

などが候補になります。

この様にデザインパターンは**設計上の問題に対する解決策**の引き出しとして利用します。

## デザインパターンは「名前」ではなく「問題と構造」が重要
次のコードがあるとします。

```typescript
const service = new Proxy(target, {
    get(target, property) {
        console.log("access");
        return target[property];
    },
});
```

これはJavaScriptの `Proxy` APIを使用しています。

しかし、`Proxy` APIを使ったから `Proxy Pattern` というわけではありません。

本質的には

> Client
>
>   ↓
>
> Proxy
>
>   ↓
>
> Real Object

という
> 本物のオブジェクトへのアクセスを代理オブジェクト経由にする

構造を採用しているため、`Proxy Pattern` と呼ばれます。

デザインパターンを理解するときは
> 「何というAPIを使っているか」

ではなく
> 「どのような設計上の問題をどの様な構造で解決しているか」

を見ることが重要です。

## デザインパターンには適用範囲がある
「デザインパターン」という言葉は広く使われています。

ただし、全てのパターンが同じ範囲の問題を解決するわけではありません。

> オブジェクト
>
>    ↓
>
> モジュール
>
>    ↓
>
> アプリケーション
>
>    ↓
>
> システム全体

の様に対象とする範囲が異なります。

### オブジェクトレベル
> Observer
>
> Strategy
>
> Factory
>
> Proxy
>
> Adapter

などは主にオブジェクトやクラス、関数の関係を扱います。

> Object A
>
>    ↓
>
> Object B

のような比較的小さな範囲の設計問題です。

### モジュール・アプリケーションレベル
一方で

> Module
>
> Repository
>
> Service Layer
>
> Dependency Injection
>
> MVC

などはより大きな範囲の設計を扱います。

例えば

> Application  
> ┣━ Controller  
> ┣━ Service  
> ┗━ Repository  

の様にアプリケーション内の責務を分離します。

### システムレベル
さらに

> Microservices
>
> Event-Driven Architecture
>
> CQRS

などは複数のサービスやシステム全体の構成を扱います。

> Service A
>
>    ↓
>
> Service B
>
>    ↓
>
> Service C

の様なより大きな設計問題です。

## 代表的なデザインパターンと解決する問題
ここまでの話を踏まえるとデザインパターンは
> 「どの様な問題を解決するためのパターンなのか」

で覚えると理解しやすくなります。

| 解決したい問題 | 体表的なパターン |
| --- | --- |
| オブジェクトの生成方法を隠したい | Factory |
| 生成するオブジェクトを1つに制限したい| Singleton |
| 既存のインターフェースを別の形に変換したい | Adapter |
| 既存のオブジェクトに機能を追加したい | Decorator |
| 複雑な処理を単純なAPIで隠したい | Facade |
| 本物のオブジェクトへのアクセスを代理したい | Proxy |
| 処理方法を切り替えたい | Strategy |
| 状態の変化を他のオブジェクトに通知したい | Observer |
| 状態によって振る舞いを変えたい | State |
| 処理を複数の処理に順番に渡したい | Chain of Responsibillity / Middleware |
| 依存するオブジェクトを外から渡したい | Dependency Injection |

## まとめ
デザインパターンとは
> ソフトウェア設計で繰り返し起きる問題に対する名前の付いた再利用可能な設計上の解決方法

です。

ただし、重要なのは

> パターン名を覚える
>
>      ↓
>
> コードをパターンに当てはめる

ことではありません。

むしろ

> 設計上の問題を発見する
>
>       ↓
>
> 問題に適した構造を考える
>
>       ↓
>
> 既知のパターンを解決策の候補として利用する

ことが重要です。

したがってデザインパターンは

> コードの書き方のテンプレートではなく、設計上の問題を解決するための知識体系

と考えると理解しやすいです。

そして、実際に学ぶときは

> 「このパターンは何か？」

ではなく

> 「どんな問題を解決するためにこの構造が使われるのか？」

という視点で見るとパターンの本質を理解しやすくなります。
