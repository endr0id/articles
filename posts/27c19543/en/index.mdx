# What is the Singleton Pattern?

The Singleton Pattern is **creational pattern that restricts the instantiation of a class to a single instance and provides a global point of access to that instance**.

It is used to centrally manage resources such as application configuration and loggers that should be shared across the application.

## Why is Singleton Needed?

Consider the following situation:

> "We need a class to manage application configuration, but if multiple instances are created, the configuration might become inconsistent."

### Problematic Code

With a regular class, instances can be created multiple times.

```typescript
class AppConfig {
  private theme: string = "light";

  setTheme(theme: string) {
      this.theme = theme;
  }

  getTheme(): string {
    return this.theme;
  }
}

// Problem: Multiple instances are created
const config1 = new AppConfig();
config1.setTheme("dark");

const config2 = new AppConfig();
console.log(config2.getTheme()); // "light" (config1's setting is not reflected)
```

This example has the following problems:

- Multiple instances exist independently
- Configuration changes are not shared
- It's unclear which instance holds the "correct configuration"

### Solution with Singleton Pattern

Restrict instances to one.

```typescript
class AppConfig {
  private static instance: AppConfig;
  private theme: string = "light";

  // Make constructor private to prevent external instantiation
  private constructor() {}

  static getInstance(): AppConfig {
    if (!AppConfig.instance) {
      AppConfig.instance = new AppConfig();
    }
    return AppConfig.instance;
  }

  setTheme(theme: string) {
      this.theme = theme;
  }

  getTheme(): string {
    return this.theme;
  }
}

// Usage
const config1 = AppConfig.getInstance();
config1.setTheme("dark");

const config2 = AppConfig.getInstance();
console.log(config2.getTheme()); // "dark" (references the same instance)
console.log(config1 === config2); // true
```

This implementation guarantees the following:

- `getInstance()` always returns the same instance
- The constructor is `private`, preventing external `new` calls
- Configuration is shared across the entire application

💡 **Essence**

The essence of the Singleton Pattern is not "restricting instances to one."

It is **"providing a consistent access method to state or resources that should be shared across the entire application."**

## When to Use?

The Singleton Pattern is effective in the following cases:

| Use Case | Reason |
| --- | --- |
| Application configuration | Configuration should be singular |
| Logger | Unify log output destination |
| Database connection pool | Centrally manage connection resources |
| Cache management | Share cache state |

However, avoid using it when there is no requirement for "being unique."

## When NOT to Use It?

Using singleton for the following reasons is incorrect.

### Using as a Global Variable Replacement

```typescript
// ❌ Bad example: Using Singleton as a replacement for global variables
class GlobalState {
  private static instance: GlobalState;
  public userData: any;
  public appState: any;
}
```

Responsibilities become unclear and implicit dependencies increase.
Required objects should be passed explicitly via Dependency Injection (DI).

### Using Just to Have One Instance

```typescript
// ❌ Bad example: Making it a Singleton without reason
class UserService {
  private static instance: UserService;
  static getInstance(): UserService {...}
}
```

Cannot replace with mocks during testing, and difficult to change when multiple instances become necessary.
Managing lifecycle with a DI container is more flexible.

### Managing Per-User State on Server-Slide

```typescript
// ❌ Dangerous: Managing user state with Singleton on server-side
class UserSession {
  private static instance: UserSession;
  private currentUser: User | null = null;
  // Shared across multiple requests
}
```

The same instance is shared across multiple requests, causing critical security issues.
Generate a new instance per request.

## Cautions When Using

When adopting Singleton, understand these 3 cautions:

### 1. Testing Becomes Difficult

Since Singleton shares state, state may persist between tests.
You need to provide a reset method for each test or manage lifecycle using a DI container.

### 2. Increases Implicit Dependencies

Since Singleton is "accessible from anywhere," dependencies don't appear in constructors and become less visible.
Explicitly passing dependencies makes the code's intent clearer.

### 3. Initialization in Multi-threaded Environments

When `getInstance()` is called simultaneously from multiple threads, multiple instances may be created.
Countermeasures are needed depending on the language or framework.

## Summary

The Singleton Pattern is "a pattern that restricts instances to one and provides a global point of access."

💡 **Key Points**

- **Identify use cases** - Use only for resources that should be shared application-wide
- **Not a global variable replacement** - Don't use just because you "want access from anywhere"
- **Trade-off with test isolation** - State sharing makes testing difficult
- **Prioritize DI** - In many cases, DI containers can manage more flexibly

Always consider whether "an instance really needs to be singular."
