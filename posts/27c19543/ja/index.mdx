# Singletonパターンとは？

Singletonパターンはインスタンスを1つに制限し、グローバルなアクセスポイントを提供する生成パターンです。

アプリケーション設定やロガーなど、全体で共有すべきリソースの一元管理に使用します。

## なぜSignaletonが必要なのか

次の様な状況を考えてみます。

> 「アプリケーション設定を管理するクラスが必要だが、複数のインスタンスが作られると設定が矛盾する可能性がある」

### 問題のあるコード

通常のクラスでは何度でもインスタンスを生成できます。

```typescript
class AppConfig {
  private theme: string = "light";

  setTheme(theme: string) {
      this.theme = theme;
  }

  getTheme(): string {
    return this.theme;
  }
}

// 問題: 複数のインスタンスが作られる
const config1 = new AppConfig();
config1.setTheme("dark");

const config2 = new AppConfig();
console.log(config2.getTheme()); // "light" (config1の設定が反映されていない)
```

この例では次の問題があります。

- 複数のインスタンスが独立して存在する
- 設定の変更が共有されない
- どのインスタンスが「正しい設定」を持つか不明

### Singletonパターンによる解決

インスタンスを1つに制限します。

```typescript
class AppConfig {
  private static instance: AppConfig;
  private theme: string = "light";

  // コンストラクタをprivateにして外部からのnewを禁止
  private constructor() {}

  static getInstance(): AppConfig {
    if (!AppConfig.instance) {
      AppConfig.instance = new AppConfig();
    }
    return AppConfig.instance;
  }

  setTheme(theme: string) {
      this.theme = theme;
  }

  getTheme(): string {
    return this.theme;
  }
}

// 使用例
const config1 = AppConfig.getInstance();
config1.setTheme("dark");

const config2 = AppConfig.getInstance();
console.log(config2.getTheme()); // "dark" (同じインスタンスを参照)
console.log(config1 === config2); // true
```

この実装では次のことが保証されます。

- `getInstance()` は常に同じインスタンスを返す
- コンストラクタが `private` なので外部から `new` できない
- アプリケーション全体で設定が共有される

💡 **本質**

Singletonパターンの本質は「インスタンスを1つに制限すること」ではありません。

「アプリケーション全体で共有すべき状態やリソースへの一貫したアクセス方法を提供する」です。

## いつ使うか？

Singletonパターンは次の様な場合に有効です。

| 使用場面 | 理由 |
| --- | --- |
| アプリケーション設定 | 設定は1つであるべき |
| ロガー | ログの出力先を統一したい |
| データベース接続プール | 接続リソースを一元管理したい |
| キャッシュ管理 | キャッシュの状態を共有したい |

ただし「唯一である」という要件がない場合は使用を避けます。

## いつ使わないか？

次のような理由でSingletonを使うのは誤りです。

### グローバル変数の代替として使う

```typescript
// ❌ 悪い例: グローバル変数の代わりにSingletonを使う
class GlobalState {
  private static instance: GlobalState;
  public userData: any;
  public appState: any;

  // ...
}
```

責務が不明確になり、暗黙的な依存関係が増えます。
必要なオブジェクトは明示的に依存性注入（DI）で渡すべきです。

### インスタンスを1つにしたいだけで使う

```typescript
// ❌ 悪い例: 特に理由なくSingletonにする
class UserService {
  private static instance: UserService;
  static getInstance(): UserService {...}
}
```

テスト時にモックに差し替えられず、将来複数インスタンスが必要になった時に変更が困難です。
DIコンテナでライフサイクルを管理する方が柔軟です。

### サーバーサイドでユーザーごとの状態を管理する

```typescript
// ❌ 危険: サーバーサイドでユーザー状態をSingletonで管理
class UserSession {
  private static instance: UserSession;
  private currentUser: User | null = null;
  // 複数のリクエストで共有されてしまう
}
```

複数のリクエストで同じインスタンスが共有され、セキュリティ上の重大な問題を引き起こします。
リクエスト毎に新しいインスタンスを生成すべきです。

💡 **判断基準**

- アプリケーション全体で唯一であるべき: Singleton
- グローバルにアクセスしたいだけ: DI

## 使う場合の注意点

Singletonを採用する場合、次の3つの注意点を理解しておく必要があります。

### 1. テストが困難になる

Singletonは状態を共有するため、テスト間で状態が残ります。

テスト毎にリセットするメソッドを用意するか、DIコンテナでライフサイクルを管理する必要があります。

### 2. 暗黙的な依存関係が増える

Singletonは「どこからでもアクセスできる」ため、依存関係がコンストラクタに現れず見えにくくなります。

明示的に依存関係を渡す方がコードの意図が明確になります。

### 3. マルチスレッド環境でも安全

複数のスレッドから同時に `getInstance()` が呼ばれた場合、複数のインスタンスが生成される可能性があります。言語やフレームワークに応じた対応が必要です。

## まとめ

Singletonパターンは「インスタンスを1つに制限し、グローバルなアクセスポイントを提供する生成パターン」です。

💡 **ポイント**

1. **使用場所を見極める** - アプリケーション全体で共有すべきリソースや状態にのみ使用する
2. **グローバル変数の代替ではない** - 「どこからでもアクセスしたい」という理由だけで使わない
3. **テスト容易性とのトレードオフ** - 状態共有でテストが困難になる
4. **DIを優先検討** - 多くの場合、DIコンテナで柔軟に管理できる

「本当にインスタンスが1つである必要があるか」を常に検討すべきです。
